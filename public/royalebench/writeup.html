Overview

Clash Royale is more than a game; it is our team’s childhood. As players ourselves, we know how difficult this game is: resource management, exploding game states, and strategic planning with imperfect information.

We have seen LLM’s play chess and poker, but we wanted to make a more unique benchmark relevant to today’s cultural zeitgeist. That benchmark is what we have to show today–RoyaleBench.

We represented 21 unique tasks using Harbor task format, Valkyrie framework, and modal compute. We isolated agents in their own game environments and gated decisions w/ a referee that determines move legality.

Our best performing model was Opus 5.5, with a pass rate of 66.7%. The average performance was 36% across 12 different LLM models.

This benchmark highlights how LLM’s still lack understanding in complex scenarios with many variables: different cards, unique interactions, and long term planning. We hope that this benchmark serves as a goal for labs to target when developing and modernizing future models. And one day, maybe we will have an LLM capable of beating Ojas (our talented friend).

Background

Clash Royale requires managing elixir, choosing deployment positions and timing, and balancing defense with tower pressure. RoyaleBench tests these decisions in fixed mid-match continuations in a deterministic simulator, verified by independent replay.

Decide when to spend elixir and when to reserve it.

Planning and adaptation

Tasks

Each task fixes the decks, hand, elixir, tower health, units, seed, opponent settings, and scoring window. The model continues from that position.

Scoring: 12 tasks require terminal match wins; nine use other objectives, including damage limits and constrained defenses. Each task contributes one binary reward.

Inside one task

What the model receives

A text observation with its hand, next card, elixir, tower HP, visible units, recent events, and time left. The opponent's hand and elixir remain hidden. Arena graphics on this page visualize the recorded state; the evaluated models do not receive these images.

How it acts

cr                 # inspect; no time advances
cr play SLOT X Y   # deploy at chosen coordinates
cr wait            # advance one decision interval

Slots are zero-based. Coordinates use the player's frame on an 18 × 32 tile arena. Task-specific intervals are 0.5, 1, or 2 seconds.

Methodology

  1. 1Observe

    The referee exposes the player's text view of the fixed position.

  2. 2Decide

    The model selects a card and coordinates, or waits. Thinking pauses time.

  3. 3Advance

    The engine applies actions and advances the task's interval. The loop repeats.

  4. 4Replay

    A separate verifier checks the log, ticks, decisions, and resulting state.

  5. 5Score

    Reward is one only when integrity passes and every objective is met.

Opponent: the Planner

Planner is a deterministic search bot with a ten-second look-ahead, three plies, four top candidates, and three responses per candidate. It reads the true engine state, including both hands and elixir. Some tactical windows permit no further enemy plays.

Task construction

Tasks use the Harbor directory format, run through Valkyrie in Modal sandboxes, and expose the protected cr interface. A separate referee owns the engine state and action log. The verifier replays the commands independently; there is no model-based judge.

Scoring and variance

Score = 100 × objectives passed / 21. Spending, damage, crowns, and match outcomes are diagnostics unless the task explicitly uses them. A terminal win can fail a stricter task objective; a defensive-window success need not end the match.

Each model has one recorded attempt per task. These results do not estimate run-to-run variance.

Limitations

  • One attempt per task. There are no estimates of run-to-run variance or uncertainty intervals.
  • Tasks were developed using model feedback. Earlier cohorts and harder variants were selected partly from Opus and Sonnet behavior; this is not a held-out evaluation.
  • Harnesses differ. Models use Claude Code, Codex, or mini-SWE-agent, with recorded harness-specific settings. The four mini-SWE runs have step_limit=12; 62/84 tasks terminate at that limit, and 33/84 are incomplete. Some scenarios require more moves than that budget supports under one-move-per-call play.
